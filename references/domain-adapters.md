# Domain Adapters

Use adapters to choose **domain-native axes** and to detect likely collapse. These are not answer keys. Treat named patterns as common attractors to mutate away from after the first use.

## How to use any adapter

1. Pick 5-8 axes that matter for the user’s domain.
2. List the obvious bubbles for this exact problem.
3. Name the common attractors the model will likely reuse.
4. Generate frames that differ across mechanism DNA.
5. Collision-check with the domain taxonomy in `references/collision-taxonomies.md`.

## GTM / distribution

Use for startup GTM, market entry, category creation, growth, launch, sales motion, distribution, adoption.

Mechanism DNA axes:

- primary adopter
- real buyer / power holder
- trigger moment
- carrier artifact
- trust mechanism
- adoption pressure
- propagation vector
- monetization or mandate path
- failure mode

Banned default bubbles usually include:

- SEO/content marketing as generic demand capture
- paid ads
- generic PLG
- generic community
- generic partnerships
- founder-led posting
- cold outbound
- influencer campaigns
- “go viral”

Common attractors to mutate, not copy:

- receiver-mandated adoption
- artifact-carried distribution
- proof / attestation loops
- category enemy creation
- workflow infection
- professional standard capture
- risk / liability mandate
- status anxiety
- habit / relief loop

Fresh-mechanism questions:

- Who benefits from forcing someone else to use this?
- What artifact already travels between people and could carry the product/result?
- What moment creates shame, fear, pride, or liability?
- What would make non-use suspicious?
- What distribution path exists without the company talking?

## Coding / software architecture

Use for architecture, refactoring, code design, system shape, developer tooling, pipelines, data flows, reliability approaches, implementation directions.

Mechanism DNA axes:

- dominant failure mode
- boundary / interface
- data-flow or control-flow shape
- state ownership
- isolation model
- observability artifact
- migration path
- reversibility
- operational blast radius
- failure mode of the proposed approach

Banned default bubbles usually include:

- “use microservices”
- “add queues”
- “add retries”
- “use caching”
- “add tests”
- “make it modular”
- “use event-driven architecture”
- “add observability”

Common attractors to mutate, not copy:

- customs checkpoint
- quarantine zone
- compiler / type-checking layer
- append-only ledger
- circuit breaker
- source-of-truth court
- reconciliation loop
- reversible migration bridge
- sandboxed workbench
- control tower

Fresh-mechanism questions:

- Where should invalid state be impossible rather than handled later?
- Which boundary absorbs mess so the rest of the system stays boring?
- What needs a chain of custody instead of a mutable latest-state table?
- What can be made reversible before it is made elegant?
